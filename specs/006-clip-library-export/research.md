## Stream and metric truth

**Decision**: List Twitch `Get Videos` archive results (`type=archive`, newest first), page size 20, provider cursor bound to creator. Cache each page under existing `TwitchCacheType.User`, key `broadcasts:<creator>:<cursor>`, with an explicit fetchedAt in its value, five-minute freshness and24-hour physical retention; serve last known data with stale indication on outage. No new schema.
**Rationale**: Includes available broadcasts with no clips without introducing permanent stream ingestion. Resolve details by VOD ID and verify broadcaster ownership; clips associate only through `video_id`.
**Alternatives**: Grouping by clip creation date misassigns clips created later from VODs; EventSub/history ingestion broadens v1.
**Metric semantics**: Clip views are latest known lifetime counters, not views gained during the date window and not VOD views. The creation window filters which clips are counted. Missing VOD metadata never removes clips from inventory.
**External evidence**: [Twitch Get Videos](https://dev.twitch.tv/docs/api/reference/#get-videos) returns published video metadata and supports user/type/pagination filters. [Twitch Clips guide](https://dev.twitch.tv/docs/api/clips/) documents that a current-broadcast clip may lack VOD ID/offset. Historical completeness cannot be inferred from these endpoints.

## Export transport and resource limits

**Decision**: Request-local bounded ZIP through an authenticated POST route; fetch at most two media files concurrently, store ZIP entries uncompressed, keep total media at 128 MiB and each item at 32 MiB, at most 50 selected clips. Client consumes a binary response into a bounded Blob, initiates one download, then revokes object URLs. Return a small JSON result header (base64url UTF-8, bounded; request-position indices/reason codes only) describing included/skipped request indices; full public metadata is in `manifest.json`. Client never parses the full ZIP merely to show feedback.
**Rationale**: Reuses fflate and established binary responses without queues, storage provisioning, multi-replica affinity or a permanent export model. Explicit caps bound server/client buffering; package peak memory must be measured before acceptance, especially on mobile. Larger exports require separate selections in v1.
**Details**: Assemble complete validated MP4 entries before ZIP response; max 128 MiB includes media only and max 1 MiB manifest, so final archive must fit 130 MiB. Cap final response and client reader at 130 MiB, account for assembly copies, release buffers promptly. If a file exceeds remaining allowance, skip it with `package_size_limit` and continue only if budget remains. Server original selection order determines byte-budget inclusion even when two fetches overlap. The UI says partial and offers retry only for retryable failures. Do not auto-retry size/missing/scope failures. All failed => typed JSON, no ZIP. Cancellation aborts fetch/read/compression; no background continuation or progress percentages without real byte evidence.
**Alternatives**: Unlimited in-memory archives risk crashes; durable jobs/object storage are unnecessary for this bounded v1. Streaming a ZIP directly into browser navigation complicates reliable partial-failure reporting and is deferred until larger export demand justifies it.

## Provider and trust boundaries

**Decision**: Use official Get Clips Download only for export, request URLs just before fetching, prefer landscape then portrait; do not change playback fallback behavior.
**Evidence**: [Twitch Get Clips Download](https://dev.twitch.tv/docs/api/reference/#get-clips-download) documents temporary URLs, scoped broadcaster/editor authorization and 100 requests/minute. The current endpoint accepts at most10 clip IDs per request; resolve a50-clip package in at most5 batches. Revalidate this documented contract during implementation and match returned clip IDs exactly; never accept an unrelated first response row.
**Controls**: Existing creator credentials remain server-side; request schema accepts IDs only, never media URLs. Apply existing rate-limit service by actor/creator, two concurrent media fetches and three export starts per minute; do not assume this replaces Twitch's endpoint quota. On provider 429 return retry information from provider reset with no busy retry. 30-second per-file and 120-second whole-request deadlines. Check current grant before starting each bounded media batch and immediately before emitting the ZIP. Restrict HTTPS media host to exact `production.assets.clips.twitchcdn.net` initially, as documented by the official endpoint sample, validate each redirect before following, reject credentials/ports/private hosts, check MP4 content and actual bytes; media fetch has no provider auth headers. There is no existing video-host policy to borrow: thumbnail/account-avatar policies are not media authorization. Bound redirects to three. Any additional provider CDN host needs official evidence and a specific allowlist fixture; never allow arbitrary cloudfront or wildcard domains.
