# Research: Free Runner and Pro Broadcasting

Date: 2026-10-14. Scope: confirmed Free manual one-broadcast/one-target access with unlimited hours, and Pro scheduling/multistreaming/branding. This is design evidence, not executed product validation.

## 1. Access and owner-wide concurrency

**Decision:** Add a Runner capability resolver that gives all authenticated eligible owners basic Runner access. Effective Pro alone gives Runner Pro capabilities, including valid Pro grants, trials and agency creator seats. Retire the unreleased Runner-only entitlement and agency Runner seats. Resolve using the resource owner inside the mutation transaction.

**Rationale:** `src/app/lib/entitlements.ts` currently makes Runner access independent of Pro, including batch resolution and reconciliation. `src/app/actions/runner.ts`, enrollment/heartbeat and `src/server/resources/workflow.ts` all contain paid gates. Changing only UI or dashboard actions leaves inconsistent access and bypasses. Lock owner then applicable entitlement/allocation and resource rows in a consistent order; every start uses the same admission service.

**Alternatives considered:** Device count limits (restrict legitimate device switching); client-only active-count checks (race/bypass); gating by operator plan (team permission escalation).

## 2. Offline state and recovery

**Decision:** Free official clients require a renewable signed 300-second execution lease. Missing heartbeat marks uncertainty, not inactivity. At lease expiry stop queuing clips and drain; output must close within an additional 300 seconds (60 seconds without progress). Server recovery waits until the last issued lease deadline plus 305 seconds or a matching terminal ACK. Persist expiry and tombstones under the owner lock, so delete/unlink never bypasses occupancy. Old non-leased executions require terminal reconciliation; never retrospectively assume a lease.

**Rationale:** Existing ~30-second offline telemetry cannot establish that RTMP stopped. Bounded local enforcement avoids both immediate bypass and indefinite occupation after device loss. A Clipify control outage longer than five minutes can stop Free output; hours remain unlimited, but supported Free execution requires periodic connectivity. Pro retains signed cached offline scheduling. Explain this connectivity difference clearly.

**Alternatives considered:** Infinite uncertain occupation blocks recovery; timeout-only server release lets a still-streaming official client bypass limits. A modified self-hosted binary can ignore enforcement because Clipify does not control the user's PC or destination. Do not claim DRM or spend this feature trying to prevent arbitrary modified clients.

## 3. Existing transport and versioning

**Decision:** Extend existing HTTP POST `/api/runner/heartbeat` polling as protocol v2. Exchange configuration revisions, capability reports, admissions/occurrences, signed benefit snapshots, targets, branding and output state. Do not replace Runner control with WebSockets. Keep overlay playback WebSockets as the separate presentation channel.

**Rationale:** `packages/runner/src/index.ts` polls heartbeat; current jobs contain a scalar target/key and state. Introduce capability negotiation so old clients cannot silently omit attribution, drain or Free admission enforcement. Require supported v2 before starting new-policy sessions; emit update-required errors for older clients. Keep old enum values `24/7`, `24_7`, `failsafe` and translate visible labels separately.

**Alternatives considered:** Full transport rewrite (unnecessary); public query flags establishing Runner identity (forgable and risks branding normal overlays).

## 4. Multiple targets using one encode

**Decision:** Share one Chromium capture and H.264/AAC encode for compatible targets. Use FFmpeg tee plus FIFO isolation/recovery with explicit stream maps, bounded queues, overflow dropping and keyframe recovery. For live input, retain stream-copy forwarding when the input codecs are compatible. Add target-specific connection/retry observations and credential-safe logs. No per-target transcoding in this release.

**Rationale:** `packages/runner/src/engine.ts` currently encodes generated playback once but forwards live RTMP with `-c copy`. The [FFmpeg tee documentation](https://ffmpeg.org/ffmpeg-formats.html#tee) supports single-encode distribution; [FIFO documentation](https://ffmpeg.org/ffmpeg-formats.html#fifo) supplies recovery/isolation controls. `onfail=ignore` alone does not retry. Aggregate process liveness is not target success; bundled FFmpeg loopback tests must prove telemetry and independent reconnection. Bandwidth grows with destination count; no unmeasured hardware capacity promise.

**Alternatives considered:** One browser/encoder per target (wasteful); unrestricted separate FFmpeg processes without isolation (can block/restart healthy outputs); retaining one target per Pro broadcast (fails agreed multistreaming scope).

## 5. Source and ingest boundaries

**Decision:** Retain the existing overlay as the clip source; do not invent a separate playlist execution path. A schedule selects an owned overlay and optionally its playlist configuration through existing source rules. In the initial release, one live-fallback input per Runner installation is supported; independent fallback broadcasts use different registered devices. Several destinations from that one input are supported on Pro.

**Rationale:** The current OBS ingest proxy uses fixed ports 1935/1936 and module-global events, so several unrelated live inputs on the same installation would collide. The approved multiple-broadcast requirement is across devices. Do not add ingest-port allocation as unrelated work.

**Alternatives considered:** Multiple independent fallback ingest listeners per installation (extra configuration and lifecycle scope); renaming database modes (unnecessary migration risk).

## 6. Agenda and time handling

**Decision:** Use installed `@heroui-pro/react` Agenda/useAgenda with controlled events, week view, create/move/resize/select/delete callbacks and dialog/form/list equivalents. Convert its `CalendarDateTime` values at a single timezone adapter boundary. Expand one-time/weekly events into signed local occurrence snapshots with stable IDs and explicit offset choices. Use the existing transitive `@internationalized/date` as a declared direct dependency if imported by app/Runner production code; no new calendar library.

**Rationale:** Installed `dist/components/agenda/use-agenda.d.ts` exposes the required callbacks, but events are wall-clock calendar values rather than timezone-aware execution instants. Cache a rolling seven-day occurrence horizon and refresh on heartbeat; known benefit expiry bounds new scheduled starts. A local scheduler must reconcile restarts and avoid duplicate starts. Sleeping PCs cannot be woken by Clipify. Clock rollback cannot resurrect a completed occurrence.

**Alternatives considered:** Calendar date picker (no event editing); paid dependency shopping (access already exists); server-only scheduler (fails local temporary-disconnection requirement).

## 7. Schedule rules and graceful end

**Decision:** Reject same-Runner event overlaps using half-open windows; merge adjacent equal source/target sets, otherwise delay next start until current clip drains and skip if that next window ended. Weekly spring-forward gaps skip with an explanation; fall-back repeated times run at the first occurrence only. Persist occurrence suppression after manual stop; next recurrence may run normally. Pause automation affects new occurrences and leaves an already active event to finish its window unless stopped explicitly.

**Rationale:** The browser currently prefetches/crossfades and `Engine.stop()` hard-kills output. A generation-correlated `drain` command must disable automatic advancement, crossfade/queued-next consumption and recovery that starts another clip, then acknowledge current-clip completion. Scheduled end always drains; no checkbox. No-current-clip ends immediately. Stop after 60 seconds without progress beyond event end or five minutes maximum overrun. Stop now is explicit immediate interruption.

**Alternatives considered:** Hard-cut scheduled stops (rejected by user); unlimited drain (can leave schedules stuck); treating pause automation as hard-stop (surprising and conflicts with graceful playback).

## 8. Runner-only presentation and standby

**Decision:** Use a server-validated Runner presentation context bound to owner, Runner, admission/session and generation. Capture the resulting frontend watermark/standby. Free logo plus `Livestream powered` / `by Clipify.us` uses a readable fixed size, bottom-right by default and four allowed corners. Pro may remove it or keep it visible. Custom standby supports logo, background color/image, message and optional next-broadcast time. Ordinary overlay URLs and live forwarding do not gain branding.

**Rationale:** `src/app/overlay/[overlayId]/page.tsx` currently creates `OverlayPlayer` using overlay secret and query presentation hints. Query strings alone are not authorization. Use a dedicated authenticated presentation bootstrap/route; keep session material out of public projections and logs. Render unavailable/expired branding as baseline Free unless an already active grandfathered transition is authorized. Standby is only output during an active event/session, never a reason to stream outside its window.

**Alternatives considered:** FFmpeg watermark on all output (would decorate normal live input); overlay-wide watermark (changes unrelated browser sources); arbitrary remotely fetched images (adds SSRF and inconsistent rendering).

## 9. Credential and asset storage

**Decision:** Reuse `src/app/lib/encryption.ts` for server-side destination encryption and `packages/runner/src/storage.ts` OS keyring/protected fallback for local destination secrets. Atomic local snapshots/journals reference secrets without embedding them. Use owner-scoped database-backed small raster branding assets in this release because no existing general upload service was found; no third-party storage provisioning.

**Rationale:** The Runner already protects configuration using mode 0600/0700 and Windows ACL handling. Offline schedules require local credentials. Bound logo/background to 2 MiB each, allow PNG/JPEG/WebP only, verify decode/magic/dimensions and re-encode to remove metadata. Limit dimensions to 4096 per axis and 16 million pixels. Messages max 160 characters. Asset authorization and failed replacement must preserve previous appearance. Use installed sharp0.35.5 as a declared direct dependency for raster normalization and verify native build footprint. Store as bytea through existing Drizzle PostgreSQL custom type support, with metadata rows; schema generation remains workflow-owned.

**Alternatives considered:** Unbounded base64 in every heartbeat (wasteful); external URL fetch or SVG/HTML uploads (unneeded attack surface); provisioning an object store (outside agreed scope).

## 10. Standalone Runner hard cut

**Decision:** Remove standalone Runner checkout, billing product and entitlement enum, agency Runner seats and their sales/configuration surfaces. Existing Pro, Pro grants/trials and agency creator seats remain the sole paid capability source. Never convert a retired Runner-only grant into Pro. Reject old signed checkout intents and discard retired commercial notices. No Stripe API/SDK version upgrade or live Stripe changes.

**Rationale:** The user explicitly authorized deleting unreleased Runner-only configuration and accepted loss of those records. The previous historical-compatibility decision is superseded. Edit schema sources only; generated migrations remain owned by the post-merge workflow.

**Alternatives considered:** Preserve a second Runner-only commercial path (rejected by the user); grant full Pro to Runner-only recipients (unrelated benefits); change live Stripe subscriptions (outside this work).

## 11. Native tests and gates

**Decision:** Reuse Jest app/package tests, native MCP workflow Gherkin execution and genuine Playwright browser journeys. Carry all 136 declared scenarios into one source registry. Runtime Gherkin may use a Runner-owned Jest binding adapter reusing repository scenario inventory checks, without browser/MCP copies of the same behavior. Add a real loopback receiver fixture for multi-output and process cleanup. Static/native/security gates remain mandatory; no coverage exceptions.

**Rationale:** `.github/workflows/ci.yml` independently runs/merges six coverage lanes; `scripts/merge-test-coverage.mjs` rejects stale/foreign inventory. Browser journeys and native MCP workflows have separate owners. Required evidence roles are not duplicate executions. The Runner package has no existing coverage threshold, so add explicit changed-code collection for new critical modules, protecting 90% lines/85% branches and 95%/90% admission-critical app services.

**Alternatives considered:** Full coverage on every inner-loop test (unnecessary repetition); mock-only fan-out tests (cannot prove FFmpeg FIFO behavior); flatten all ownership into browser scenarios (violates execution ownership).

## Resolution

All technical unknowns above are resolved into bounded design choices. Product quota is explicitly unlimited. Hardware performance, old-client compatibility, real receiver recovery and asset parsing are planned validation gates, not unverified guarantees. The Spec Kit setup script returns the feature directory basename as BRANCH when SPECIFY_FEATURE is unset; git confirms the actual branch is `plan/free-runner-branding`, which remains unchanged.

### Suspend-aware native execution timing

The native request timestamp, Free lease guard and graceful drain use one shared elapsed clock. It takes the conservative high-water of process monotonic time and elapsed OS uptime. Detected backwards uptime changes rebase to the previous elapsed high-water plus current process progress, so a rollback cannot freeze or extend a permit. Signed TTL remains server-issued; client wall-clock epochs are never permit authority.

Primary implementation references: [libuv Linux uptime](https://github.com/libuv/libuv/blob/v1.x/src/unix/linux.c) reads `/proc/uptime` or `CLOCK_BOOTTIME`; [libuv Windows uptime](https://github.com/libuv/libuv/blob/v1.x/src/win/util.c) uses `GetTickCount64`; [libuv Darwin uptime](https://github.com/libuv/libuv/blob/v1.x/src/unix/darwin.c) derives uptime from `kern.boottime`. Independent clock, default signed lease, CLI timestamp and Engine deadline owners cover the contract. Native fake-timer media fixtures explicitly inject their deterministic clock.

D3 persistent-clock implementation: same-boot restart anchors use system uptime plus an OS boot identity, independently of the PC wall clock. Linux reads its kernel boot UUID. macOS uses the boot-session sysctl also used by [WebKit's Darwin implementation](https://github.com/WebKit/WebKit/blob/main/Source/WTF/wtf/UUID.cpp). Windows combines the local installation identity with the [documented successful-boot counter](https://learn.microsoft.com/en-ca/windows-hardware/design/device-experiences/oem-hvci-enablement). Missing/unreadable boot identity requires fresh synchronization after restart; it never extends cached permission. Platform system calls are read-only and bounded; results are cached per store/process. Boundary tests with isolated OS responses do not claim real Windows/macOS execution; those remain owning platform gates.

D6 integration follow-up from D3 future-authority introduction (within existing override/restart tasks): audit all human Stop/Resume and read-view queries so future authorized entries do not stand in for the current physical generation or permanently disable explicit Resume. Persisted local pending generations removed by a newer signed configuration need never-opened terminal closure, while accepted active signed contexts/private references must survive a newer empty future cache during pause or paid expiry. These are unqualified later-slice lifecycle paths, not claimed by D3 offline-start acceptance. Final implementation remains No-Go until their D6 owners and integrated gates pass.

D6/F1 legacy integration audit must also cover recognizeLegacyBroadcasts: a future authorized row alone must never count as a tracked physical legacy output. Add the persisted Running legacy-session plus future-authority Given, assert an unleased uncertain claim is retained, and prove cached-authority bounded recovery cannot erase that separate legacy uncertainty. Keep this with the existing admission/override convergence work; D3's narrow offline-start gate does not claim this mixed-version integration complete.

D4 remaining integration after exact-end cycle: native controller reports currently omit an in-progress drain, so a scheduled end is not yet visibly distinguished as finishing in the dashboard until terminal closure. Add a scoped verified draining acknowledgment without claiming allOutputsClosed, persist matching current execution/session finishing intent, keep Stop-now available and require terminal physical proof for release. Reject stale/future-authorized drainer observations that could overwrite a newer physical execution. Also clear only the known finite playback-timeout message once a matching replacement broadcast is verified active; do not leave an old timeout alert on a healthy new broadcast or erase unrelated diagnostic state. Cover these through existing whole runtime/heartbeat/lease/controls owners before D4 qualification.

D4 watchdog follow-up from read-path review: initial requestDrain RPC is now bounded, but the first delayed successful snapshot currently resets lastProgressAt even though no change has been observed, and fixed250ms waits can overshoot a60s/300s boundary when RPC latency offsets the polling phase. Add a controlled delayed-first-report case; use the first snapshot only as the baseline and cap polling sleep by remaining watchdog budgets. Keep exact-boundary existing cases, real-media timeout results and physical-close proof intact. Complete this small Red/Green before the D4 gate.

Add one scoped drain test that starts a real bridge drain, calls immediate engine.stop, then awaits both callers; all resources must close once and the timeout outcome must remain absent. This also protects the Stop-now dashboard path before qualifying D4.

## D5 continuity constraints from the first physical handoff cycle

The FR014 actual-watchdog Red proves that independent cached jobs can activate concurrently when only per-session identity is checked. The minimal verified barrier now retains the previous scheduled physical owner until its terminal receipt is journaled; independent manual Pro sessions keep their existing path. The first corrected real-media cycle passes11/11 and controlled native owners79/79. The expired-successor regression is currently executing; do not mark its evidence Green in advance.

For the subsequent identical-input continuity cycle, a simple deadline extension or a proxy engine returning early from requestDrain would violate existing signed-end or physical-closure guarantees. A shared physical execution must retain each separately signed occurrence membership, validate any planned future authority without activating it before its start, preserve the player's exact-end guard unless contiguous matching authority covers that boundary, and retain every member's terminal proof until physical output closure. Source credentials/revisions, rendering quality and normalized actual destination inputs must remain captured; names alone cannot establish equivalence. Changed source/destinations must continue through the verified physical handoff barrier. These are implementation constraints, not proof that continuity is built or a change to the approved feature scope.

D5 continuity implementation now under its first outer Green run: the controller prepares separately signed matching windows, binds source revision plus complete media/target hash, preserves each original journal end, shares one physical engine, activates membership at its local boundary and emits every terminal receipt only after shared closure. This does not yet qualify D5. D6 must explicitly reconcile an already-prepared group's still-future members when a newer cache removes/revises them or fresh benefits revoke scheduling: preserve current captured membership, remove unstarted future authority, and update the generated player's effective boundary safely. Preparing a new map alone does not reconcile an existing group. Review bounded browser deadline updates, restart/member replay, logical Stop suppression, and delayed old-member Stop rejection. These remain required pending work, not accepted exceptions or permission to grandfather every prepared future event through a fresh revocation.

D5 final review candidates for controlled durability checks before qualification: future member activation persistence failure must fence new output permission and drain safely; manual Stop before a later member starts must leave that distinct pending occurrence unsuppressed and restartable. Review any trusted-clock jump across multiple member windows so an entirely elapsed future occurrence is not advertised as newly active. Separately review the pre-existing first active-journal save failure after engine.start under the feature's fail-closed durability obligations. These are review candidates requiring executable characterization, not claims of discovered product regressions or accepted exceptions.

D6 Pause automation decision: Pause disables future automatic starts while keeping Scheduled mode. An already running captured broadcast may finish its original window and remains manually stoppable; Pause does not silently switch it to Manual or extend its end. After process loss it must not automatically restart while paused. Resume automation is a separate explicit action; resuming a manually stopped current occurrence still requires the existing explicit occurrence Resume. Persist per-session pausedAt and an automation revision alongside configuration CAS revision, invalidate future cache authority, and reconcile unstarted continuity membership without revoking the already-started captured member. This resolves routine control semantics under the approved FR013/FR015 model and does not waive the native reconciliation proof.

D6 Pause revision refinement before implementation: change only the session's dedicated automation revision/paused timestamp, retaining its media configuration revision and active capture identity. Require both current media and automation CAS revisions on the action. Increment the Runner authority revision atomically so a delayed pre-Pause cache cannot be accepted at the same issuedAt timestamp. This also keeps the already-rendered parent Stop control's media revision valid immediately after Pause. The prior new-test assumption that Pause increments media revision is corrected before implementation; the intended missing-button and false-success Reds are unchanged, not weakened.

D6 review candidate: native continuity can emit multiple started logical admissions for one physical pipeline, while the server retains one physical open-admission row per session and rejects another cached active receipt whenever that row exists. Existing D5 media fixtures use separate session IDs. Characterize the actual same-session receipt/renewal lifecycle before final qualification; preserve the physical concurrency constraint rather than simply weakening it. This is a pending review candidate, not a verified regression or completed requirement.

D6 follow-up review candidates after the exact-boundary cycle: server issueRunnerScheduleCache currently skips every same-session future occurrence whenever another physical occurrence is active, so a fresh ordinary heartbeat may trim an intended adjacent continuation. Characterize through the real cache issuer, not fixture-generated authorizations. Deadline propagation also needs stalled-browser RPC/output fencing, refresh/reload bootstrap, and rejection-after-terminal ordering evidence before final qualification. These are review candidates to test, not claimed completed behavior.

D6 candidate design notes, unimplemented/unqualified: unseen cached admission replay can be rejected by consulting persisted occurrence-level suppression across all journal records, keyed by owner/Runner/occurrence rather than admission ID. Preparing a matching future member must also inherit suppression so continuity cannot bypass apply. Any later explicit Resume needs a separately trusted control intent; arbitrary higher media revision is insufficient. Existing journal retention keeps terminal records through max(updatedAt, occurrence.end) plus seven days, covering signed cache lifetime, but bounded writes and clock rollback still need qualification.

Same-session continuity candidate (requires evidence and review before source changes): distinguish a logically continued prior admission from a physical active admission, preserving original occurrence ends and all-output closure receipts. A dedicated continued state could be excluded from the one-physical-execution unique index while remaining nonterminal for occupancy and acknowledgments. Atomically transferring the physical representative would require exact verified adjacency, same captured source/settings/targets and Pro cache authority; older member active receipts must never reactivate its physical row. Future cache issuance must not disappear merely because an earlier occurrence on that session is active. No concurrency constraint should be weakened without this ownership model and real database/CLI tests. This note is a candidate, not an approved completed design or migration request.

D6 explicit Resume design before implementation: ordinary signed execution is issued only for explicit owner Start/Resume intent, while automatic authority has the separate scheduled_execution purpose. Include immutable occurrence ID/start/end in that existing ordinary signed purpose and delivered job. Persist an explicitResume marker on the verified accepted admission's occurrence metadata, tied to its signed configuration revision. Occurrence control high-water derives from durable suppressed and explicitly resumed records; the latest Stop wins ties, cached admissions below the high-water stay blocked, and a higher cached media revision never clears Stop. A later verified ordinary Resume may clear only by advancing that control revision. Preserve Resume metadata when a cold cached job resumes the same admission. No new pricing tier, hosted media, journal secret or generated database migration is needed for this control metadata.

### D6 shared-session physical ownership design

Real media already retains two logical receipts for one shared capture when both events use the same session. Persist that relationship with a nullable continuity-root admission ID on later members, rather than inventing an ended/closed state for the first still-open member. Both remain active/draining until actual physical closure. The existing one-open-physical-session unique index applies only to root admissions; members may bypass it only after the owner-locked acknowledgement verifies an active, unrevoked, exactly adjacent group with identical signed capture fingerprint. A composite owner/root foreign key prevents cross-owner linkage; roots cannot link themselves. No generated migration on this branch. Ordinary cache refresh must bind captured media only to the matching occurrence while retaining other future rights, and automatic cache deliveries must not become owner Resume commands. Add negative chaining/closure proofs before qualifying the resulting behavior.
